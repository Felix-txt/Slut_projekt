Backend needs for external game cloud-save integration
=====================================================

Important scope
---------------
Only change this backend project. Do not modify the game project, do not write Lua code, and do not assume the backend files will live inside the game repo.

The game is a separate client. It will later call this Node/Express API for account login and cloud saves.

Goal
----
Make the backend expose a stable API contract that the game can depend on:

1. Register account
2. Login account
3. Save a full cloud-save snapshot as JSON
4. Load that cloud-save snapshot back unchanged
5. Support leaderboard later from saved JSON data

Current important mismatch
--------------------------
The backend already has auth and saves routes, but the responses and save format need to follow the game's needs.

The game should not adapt to random backend response shapes. The backend should return a clean, consistent contract.

Required response format
------------------------
All successful auth/save responses should include:

{
  "ok": true
}

All failed auth/save responses should use:

{
  "ok": false,
  "errorType": "validation | auth | server",
  "errorMessage": "Human readable error"
}

Recommended HTTP status codes:

- 400 validation errors
- 401 invalid login or invalid token
- 403 valid token but forbidden access
- 500 server/database errors

Auth requirements
-----------------
POST /api/auth/register

Request body:

{
  "username": "PlayerName",
  "email": "player@example.com",
  "password": "password123"
}

Success response:

{
  "ok": true,
  "accountId": 1,
  "email": "player@example.com",
  "username": "PlayerName"
}

POST /api/auth/login

Request body:

{
  "email": "player@example.com",
  "password": "password123"
}

Success response:

{
  "ok": true,
  "token": "jwt-token-here",
  "accountId": 1,
  "email": "player@example.com",
  "username": "PlayerName"
}

Login failures should return 401, for example:

{
  "ok": false,
  "errorType": "auth",
  "errorMessage": "Fel e-post eller losenord."
}

JWT / middleware requirements
-----------------------------
The JWT should identify the account. Either keep the existing payload or standardize it.

Recommended JWT payload:

{
  "accountId": 1,
  "email": "player@example.com"
}

The auth middleware should set:

req.userId = decoded.accountId
req.accountId = decoded.accountId

If you keep the old payload { userID: user.id }, make middleware support both:

req.userId = decoded.accountId || decoded.userID
req.accountId = req.userId

This avoids breaking older routes.

Save database requirements
--------------------------
schema.sql currently appears to be missing the saves table used by controllers/savescontroller.js.

Add this table:

CREATE TABLE IF NOT EXISTS saves (
  id SERIAL PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  game_id VARCHAR(100) NOT NULL,
  save_data JSONB NOT NULL,
  version INTEGER NOT NULL DEFAULT 1,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(user_id, game_id)
);

CREATE INDEX IF NOT EXISTS idx_saves_user_game ON saves(user_id, game_id);
CREATE INDEX IF NOT EXISTS idx_saves_save_data_gin ON saves USING GIN (save_data);

Save endpoint requirements
--------------------------
Keep the existing route if you want:

POST /api/saves/save

It must require:

Authorization: Bearer <token>
Content-Type: application/json

Request body expected from the game:

{
  "gameId": "case-clicker",
  "snapshot": {
    "name": "Player",
    "money": 1234,
    "level": 10,
    "inventory": [],
    "inventoryCount": 0,
    "stats": {
      "totalCasesOpened": 50,
      "totalValue": 1000,
      "totalSpent": 500,
      "playTime": 3600,
      "firstPlayed": 1716800000,
      "lastPlayed": 1716807200
    },
    "savedAt": 1716807200
  }
}

Store snapshot directly in saves.save_data as JSONB.

Important:

- Do not try to split inventory into SQL rows yet.
- Do not throw away unknown fields.
- Do not perform merge logic in the backend.
- The game handles conflict resolution.
- The backend's job is to save and load the latest accepted snapshot.
- Preserve snapshot.savedAt if the game sends it.
- If snapshot.savedAt is missing, set it server-side before saving.
- Load responses must return the saved snapshot including savedAt.

Success response:

{
  "ok": true,
  "saveId": 1,
  "version": 2,
  "savedAt": 1716807200
}

Backward compatibility:

If existing frontend code sends saveData instead of snapshot, the backend may accept both:

const snapshot = req.body.snapshot || req.body.saveData;

But responses for this game should use snapshot.

Load endpoint requirements
--------------------------
Keep the existing route if you want:

GET /api/saves/load/:gameId

It must require:

Authorization: Bearer <token>

Success response when a save exists:

{
  "ok": true,
  "snapshot": {
    "name": "Player",
    "money": 1234
  },
  "version": 2,
  "updatedAt": "2026-04-27T12:00:00.000Z"
}

Success response when no save exists:

{
  "ok": true,
  "snapshot": null
}

Snapshot contract
-----------------
The backend should accept this general shape, but should also allow extra fields:

{
  "name": "Player",
  "money": 1234,
  "level": 10,
  "inventory": [],
  "inventoryCount": 0,
  "stats": {
    "totalCasesOpened": 50,
    "totalValue": 1000,
    "totalSpent": 500,
    "playTime": 3600,
    "firstPlayed": 1716800000,
    "lastPlayed": 1716807200
  },
  "savedAt": 1716807200
}

Validation requirements:

- gameId is required.
- snapshot must be a JSON object.
- snapshot may be large.
- unknown snapshot fields must be preserved.

Express JSON limit
------------------
Inventory can become large. Change:

app.use(express.json());

to:

app.use(express.json({ limit: "10mb" }));

Potential schema issue
----------------------
The backend also has /api/games routes, but schema.sql appears to be missing a games table.

Either:

1. Add a games table to schema.sql, or
2. Remove/disable /api/games routes until they are needed.

Leaderboard later
-----------------
Later we want:

GET /api/leaderboard?sort=level|money|casesOpened&limit=50&offset=0

Possible response:

{
  "ok": true,
  "rows": [
    {
      "accountId": 1,
      "username": "PlayerName",
      "level": 10,
      "money": 1234,
      "totalCasesOpened": 50,
      "inventoryCount": 20,
      "updatedAt": "2026-04-27T12:00:00.000Z"
    }
  ]
}

This can be built from saves.save_data JSONB later using expressions like:

(save_data->>'level')::numeric
(save_data->>'money')::numeric
((save_data->'stats')->>'totalCasesOpened')::numeric
(save_data->>'inventoryCount')::numeric

Startup sync rule used by the game
----------------------------------
When a remembered account enters the game, the client will:

1. Build a local snapshot.
2. Load the cloud snapshot from GET /api/saves/load/:gameId.
3. Compare snapshot.savedAt.
4. If cloud savedAt is newer than local savedAt, the client downloads cloud and overwrites local.
5. Otherwise, the client uploads the local snapshot.

Because of this, savedAt must be a Unix timestamp in seconds and should be preserved accurately.

Definition of done
------------------
This backend is ready for the game's first integration when:

1. Only backend files are changed.
2. POST /api/auth/register returns ok/accountId/email/username.
3. POST /api/auth/login returns ok/token/accountId/email/username.
4. Auth middleware sets req.userId for protected routes.
5. schema.sql creates the saves table.
6. POST /api/saves/save accepts { gameId, snapshot }.
7. GET /api/saves/load/:gameId returns { ok: true, snapshot }.
8. A saved snapshot loads back unchanged.
9. Auth/save errors return { ok: false, errorType, errorMessage }.
10. express.json uses at least a 10mb limit.
